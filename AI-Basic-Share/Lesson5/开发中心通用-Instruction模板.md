# 开发中心通用 Instruction 模板

> 适用场景：需要长期固定 AI 的输出结构、语言风格、关注点、禁止行为与优先级规则时使用。
> 使用原则：Instruction 只写长期有效、跨任务可复用的规则；一次性的业务背景、临时需求和单次任务目标应留在 Prompt 中。

---

## 先说结论

一份适合开发中心共享的 Instruction，建议至少包含以下四类信息：

1. 文件头元数据：说明这份规则的用途和适用范围。
2. 规则正文：明确必须遵守的输出结构、关注点和禁止行为。
3. 优先级与例外：明确先看什么、什么时候不适用。
4. 示例与维护信息：方便别人拿来即用，也方便后续维护。

如果希望 Copilot 更容易在合适场景自动命中，建议在文件开头加入 frontmatter。

---

## 推荐文件头

```markdown
---
description: "用于统一代码 Review 的输出结构、风险排序与关注点，适用于后端接口、脚本和数据库操作审查。"
applyTo: "**/*.{py,java,js,ts,sql,md}"
---
```

说明：

- `description`：必须写清“这份规则在什么场景下使用，以及主要解决什么问题”。
- `applyTo`：必须控制作用范围，避免全仓库误匹配。
- 一般不必额外增加无明确用途的元数据字段。

---

## 标准模板

```markdown
---
description: "[说明这份 Instruction 的用途、适用对象和目标结果]"
applyTo: "[填写适用文件范围，例如 **/*.py 或 src/**/*.ts]"
---

# [Instruction 名称]

## 目的
[明确说明：这份规则要解决什么问题，统一什么输出，降低什么风险。]

## 适用场景
- [场景 1]
- [场景 2]
- [场景 3]

## 不适用场景
- [场景 A]
- [场景 B]

## 强制输出结构
1. [输出部分 1]
2. [输出部分 2]
3. [输出部分 3]
4. [输出部分 4]

## 重点关注项
- [关注点 1]
- [关注点 2]
- [关注点 3]

## 优先级规则
- [先看什么，再看什么]
- [如何排序，例如高 / 中 / 低]

## 语言与表达要求
- [例如：使用简洁中文]
- [例如：结论先行]
- [例如：术语保留英文原文]

## 强制约束
- 必须：[必须遵守的规则]
- 必须：[必须遵守的规则]
- 禁止：[明确禁止的行为]
- 禁止：[明确禁止的行为]

## 信息不足时的处理规则
- [例如：明确指出缺少哪些上下文]
- [例如：不要用假设填补未知信息]

## 输出质量要求
- [例如：每个问题必须说明触发条件与影响范围]
- [例如：不要只给结论，要给出判断依据]

## 示例
[给出一个最小可用示例，帮助团队成员直接套用。]
```

---

## 编写原则

### 1. 规则要可执行，不要写空话

不要写：

- 请尽量回答得更好
- 注意代码质量

建议写成：

- 必须优先检查正确性、边界条件、异常处理、测试覆盖
- 必须按高 / 中 / 低严重程度排序输出问题

### 2. 优先使用“必须 / 禁止 / 应当”这类规范语言

这会让文档更像正式规则，而不是经验建议。

推荐语气：

- 必须
- 禁止
- 应当
- 仅在以下条件下允许

避免语气：

- 尽量
- 最好
- 可以考虑

### 3. 一份 Instruction 只解决一类稳定问题

不要把代码解释、代码 Review、测试点生成、Bug 分析都混在同一个文件里。

### 4. 把“一次性任务背景”和“长期规则”分开

例如：

- “本次要审查订单模块的 submit_order 函数”属于 Prompt。
- “Review 时必须先给高风险问题，再给中低风险问题”属于 Instruction。

## 开发中心示例：代码 Review Instruction

```markdown
---
description: "用于统一代码 Review 的输出结构与风险排序，适用于后端接口、批处理脚本和数据库相关代码审查。"
applyTo: "**/*.{py,java,js,ts,sql}"
---

# 代码 Review Instruction

## 目的
统一开发中心代码 Review 的输出结构与风险判断标准，减少不同人员关注点不一致的问题。

## 适用场景
- 后端接口代码审查
- 批处理、脚本和定时任务审查
- 数据库读写、事务与异常处理逻辑审查

## 不适用场景
- 纯文案润色
- 不涉及代码的普通问答

## 强制输出结构
1. 高风险问题
2. 中风险问题
3. 低风险问题
4. 缺失的测试方向
5. 需要补充的信息

## 重点关注项
- 正确性
- 边界条件
- 异常处理
- 测试覆盖
- 可读性

## 优先级规则
- 必须先检查正确性，再检查异常处理，再检查可读性
- 所有问题必须按高 / 中 / 低严重程度排序

## 语言与表达要求
- 使用简洁中文
- 每个问题先给结论，再说明原因
- 每个问题必须说明触发条件与潜在影响

## 强制约束
- 必须优先指出可能导致故障、数据错误、安全风险或回归的问题
- 必须指出缺失测试的关键方向
- 禁止只给风格建议而忽略正确性问题
- 禁止在未明确要求的情况下直接大改代码

## 信息不足时的处理规则
- 如果缺少调用链、上下游接口、配置或测试上下文，必须明确指出
- 禁止使用臆测补全缺失信息
```

## 开发中心示例：代码解释 Instruction

```markdown
---
description: "用于统一代码解释输出结构，适用于新人读码、复杂函数说明和模块交接文档整理。"
applyTo: "**/*.{py,java,js,ts,sql}"
---

# 代码解释 Instruction

## 目的
统一代码解释格式，方便开发中心新人理解代码，也方便沉淀为内部说明文档。

## 适用场景
- 新人熟悉模块代码
- 复杂函数或调用链说明
- 评审前的结构理解

## 强制输出结构
1. 一句话总结功能
2. 输入参数说明
3. 核心处理流程
4. 返回值说明
5. 可能异常和边界条件
6. 需要人工确认的问题

## 语言与表达要求
- 使用简洁中文
- 关键变量名、函数名、类名保留英文原文
- 每个部分聚焦事实，不展开无依据猜测

## 强制约束
- 禁止直接修改代码
- 禁止添加代码中不存在的功能假设
- 如果调用链不完整，必须说明无法确认的部分
```

---

## 发布前检查清单

发布团队版 Instruction 前，至少检查以下项目：

- 是否写了 `description`
- 是否写了 `applyTo`
- 是否明确了适用场景和不适用场景
- 是否包含可执行的“必须 / 禁止”规则
- 是否定义了输出结构和优先级规则
- 是否附带了一个最小可用示例
- 是否避免写入一次性业务背景

---

## 维护要求

- 只保留长期有效的规则，不要把临时任务写进来。
- 每份 Instruction 应当只有一个主目标，不应混合多个无关场景。
- 团队共享版本应当标注适用范围，并附最小示例。
- 建议按月或按季度回顾一次，删除失效规则，合并重复规则。
